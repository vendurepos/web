## Check whether a sale has reached the store

The till keeps the catalogue in a local database in your browser and sells with the network off.
Each sale waits on the till until the store is reachable, then lands in Vendure once,
never twice, at the POS price, paid and fulfilled.

Read the sync status in the header:

- `N orders waiting to send`, with ` · sending…` while sending.
- `Closing — waiting for N orders` while a close waits for them.
- `N orders need attention` opens the orders list.

Open **Orders** to see the till's recent sales with a status: **Waiting to sync**,
**Synced** or **Not accepted**. Sales the store refused appear under **Needs attention**
in Orders, with a **Retry**. Choose **Back to sale** to return without losing your cart.

**Till updates line**

Till updates are the register's records the till sends to the store: opening and closing the
register, cash movements and their voids, and the closure.

- "Till updates aren't sending: this till needs to sign in to the online store again."
  Sign in to the online store again.
- "N till updates need attention · The online store refused them, and later till updates wait
  behind them. Ask the store owner to look at the sync log in this till's Settings."
  Open **Settings**, then **Sync log**, and choose **All**: the refusal is a `DEBUG` line,
  `Register command result … status=rejected errorCode=… error=…`, which **Warnings and errors** does not show.
  Copy it (**Share** on a phone) before you close or reload the app: the log holds only this till's last 500 events
  since the app opened, and the refused update is never sent again, so the line does not come back.
  What happens next depends on the `errorCode`:
  - `register_session_already_open`: the store already has this register open, on another till or from a session
    never closed there. The till offers **Choose another register**; this till's records for that session then stay
    on this till and are not sent.
  - `register_closure_number_invalid`: the till renumbers the closure and sends it again by itself, once.
  - Any other code: the till has no retry or skip, and fixing the store does not make it send the update again.
    **Sync now**, signing out and in, and closing the register do not clear it. Later till updates for this register
    stay saved on this till; sales keep syncing as normal.

  Do not clear the site's data or reinstall to get past it: that deletes this till's unsent sales, refunds and
  register records along with the refused update.
- "N till updates waiting to sync · The online store refused the last send. This till will try
  again with the next till update, or when the app is reopened."
- "Till updates aren't reaching the online store. Keep selling: they're saved on this till and
  will send by themselves."
  Keep selling.

**Store settings**

- "This store's VendurePOS plugin is missing or out of date. Install or update it, then this till continues."
  The store must advertise `order.create` v4 and register v1, as every plugin release from 0.1.0
  does. Install the current release as in [the quick start](/docs/quick-start#1-install-the-plugin),
  apply its schema changes and restart Vendure; the till retries.
- "Can't reach the store's settings yet. Retrying…"
  The till takes no sale until it has read the store's settings.

## Refresh prices and stock

An open till picks up a price change made in Vendure within about a minute and a
stock change within about five minutes. Each product shows its stock "as of" the last check.

To pull the whole catalogue fresh, sign out and sign in again. Signing out removes
the local catalogue but never the orders. Unsent orders and the register wait on
that device for the next sign-in to the same store and channel.
Sign out waits while a sale is saving ("Sign out waits until the sale is saved.")
or the register is closing.

## Sell while offline

Once the catalogue has synced, everything at the till works offline except
customer search and adding a customer, which need a connection to the store.

## Resolve a sale the store kept part-way

This section is for whoever runs your Vendure server.
A sale marked `needs_admin` answers 409 until an admin resolves it through the
Admin API with SuperAdmin access. List these sales with `tallyNeedsAdminCommands`;
each `id` is the `commandId` you resolve:

```graphql
query {
  tallyNeedsAdminCommands {
    id
    clientOrderId
    channelId
    orderId
    orderCode
    createdAt
  }
}
```

Resolve one with `tallyResolveNeedsAdmin`, using `applied` or `rejected` as the
resolution and a note:

```graphql
mutation {
  tallyResolveNeedsAdmin(
    commandId: "command-id",
    resolution: applied,
    note: "checked the till"
  ) {
    id
    status
  }
}
```

Choose `applied` when the order should stand: the plugin leaves it as recorded,
and the till's resend answers `duplicate`.
Choose `rejected` when the sale should not count: the plugin cancels the order
and its settled POS payments, and the till's resend answers `rejected`.
Either way the mutation's `status` is your resolution and the sale leaves the list;
after a rejection, the order is `Cancelled` and flagged `tallyRejected`.

Send a rejection with the sale's channel token (`vendure-token`).
An order flagged `tallyRejected` counts as never placed: leave it out of register
and sales figures, and use the till's **Retry** for the sale that counts.

## Check browser storage

If the local database cannot start, the till shows the error with a **Reload** button.
Private windows that give a site no storage, such as Safari's, cannot run the till.

## Fix CORS, 401 or plain-http store problems

Follow [Troubleshoot in the quick start](/docs/quick-start#9-troubleshoot).
A till served over https talks only to https stores; `http://localhost` and
`http://127.0.0.1` are allowed for development.

The hosted HTTPS build does **not** use the
LAN `http:` rewrite: leave `VENDUREPOS_WEB_ALLOW_LAN_HTTP` unset. That option
adds `http:` to `connect-src` and `img-src` only for exports served over
plain HTTP on the same LAN; it cannot bypass HTTPS mixed-content blocking.
