## Worst defect per judge and criterion

### C1 First impression (mean 8.4)
- J1 (8): The hero is clear ('Point of sale for Vendure', with Vendure explained in one clause), but the first thing above the h1 is the badge 'Pre-release · plugin 0.3.0', and the first proof cards go straight to developer language ('the Vendure plugin saves that id with the order in one step', 'Read the 200-send test'). A newcomer who half knows Vendure gets the what, but not who it is for (does a small shop owner do this, or their developer?). _[home/desktop/01 (badge above h1, 'Every sale lands once' card); home/phone/01-02]_
- J2 (8): The home page's 'Before you start' list mixes server requirements ('Node ^20.19 || >=22.12', 'RXDB_PREMIUM' licence token, Postgres) with what the counter needs, which sits in the 5th of 7 bullets ('At the counter: a browser on the till's device ... desktop Chrome; tablets and phones, an iPad included, are not tested yet'). A shop owner reading on a phone has to dig to see what hardware staff need tomorrow. _[home.desktop.02 'Before you start'; home.phone.04]_
- J3 (10): none found _[text/home.txt; shots/home.desktop.01.jpg; shots/home.phone.01.jpg]_
- J4 (8): The hero stacks three blocks of text before the product image: a four-line lede, the two buttons, then a second small-print paragraph ("Your own store needs the plugin on your Vendure server first..."). On a phone this pushes the till screenshot below the first screen, so the first thing a visitor sees is text, not the product. _[home.phone.01 / home.desktop.01]_
- J5 (8): The home page says what it is and gives two clear CTAs, but never says who should NOT use it or how it compares with the obvious alternative (a hosted POS such as Shopify POS or Square plus a sync); the 'Live demo or your own store' table compares the product with its own demo, not with competitors. _[home/desktop/02 ('Live demo or your own store' section)]_

### C2 Credibility (mean 8.4)
- J1 (8): The comparison table's demo cell says 'All it sends is anonymous usage events to ph.wcpos.com'. That is an unexplained third-party domain, and nothing on the home page says who makes VendurePOS (the footer only has 'Built with TallyUI. For Medusa, see MedusaPOS.'). An honest disclosure therefore leaves a first-timer asking 'who is wcpos, and who is behind this?' _[home/desktop/02 'Live demo or your own store' table, last row; home footer]_
- J2 (9): The proof buttons 'Read the acceptance test' and 'Read the 200-send test' open raw TypeScript files on GitHub (offline.spec.ts, replay.e2e.ts), with no plain-language result or date of the last passing run, so a non-developer cannot check the claim. _[home.desktop.01 'What it does today' cards; tech.json home.desktop links]_
- J3 (9): The 25-sale and 200-send claims link to test source on main, without a versioned successful run establishing those results. _[text/home.txt, 'Keeps selling offline' and 'Every sale lands once'; tech.json, home.desktop.links]_
- J4 (9): The plugin 0.3.0 refund caveat appears three times on the home page: in the comparison table row "Refund a sale at the till", in the "Coupon codes... refunds go through the Vendure Dashboard" bullet, and again behind the Limitations link. Saying it three times reads as nervous rather than plain. _[home.desktop.02]_
- J5 (7): Nobody is named behind the project: no maintainer, company, support channel or production users anywhere, and the only clue is the unexplained third-party domain in 'All it sends is anonymous usage events to ph.wcpos.com'. The changelog adds to the doubt: three plugin releases in five days (0.1.0 2026-10-01, 0.2.0 and 0.3.0 both 2026-10-06), none since, and a known gap still unpatched ('Not in the release notes: in 0.2.0 and 0.3.0 this role has no ReadOrder'). _[home/desktop/02 table row 'Sales reach Vendure'; changelog/desktop/01]_

### C3 Path to a till (mean 8.0)
- J1 (8): The quick start is complete, down to 'Check it worked', but it carries a collapsed leftover, 'If your store already allows vendurepos.vercel.app', in step 5. To a newcomer that reads as an old domain nobody cleaned up, inside the most important how-to. _[quick-start/desktop/03 top; quick-start/phone/05 bottom]_
- J2 (8): A known plugin gap is handed to the installer as a manual step: the device-key role 'vendurepos-pos-till' on plugin 0.3.0 lacks ReadOrder, 'so add ReadOrder to that role yourself', or 'the till sells but its order history is refused'. It is buried in the last optional section, which is easy to miss. _[quick-start text 'Optional: a device key for each till'; connect-a-till 'Create and use a device key']_
- J3 (8): Different global tax strategies are prescribed for inclusive and exclusive channels, but a store mixing both is only told to 'account for the store-wide strategy', leaving the configuration decision unresolved. _[Quick start, step 6, 'Why these pairings'; text/endpoint_llms_full_txt.txt:867]_
- J4 (8): Step 8 "Sign in and make a sale" is a nine-item lettered list (a–i) with no image of the sign-in or open-register screen, so the developer's first look at the real till is at the step where they are most likely to stall. The only till images are on At the till and the home page. _[quick-start.desktop.03-04 / text/quick-start.txt (no [image:] markers)]_
- J5 (8): The path is complete and ordered, with a 'Check it worked' list, but a real store hits workarounds the quick start only mentions in passing: the plugin's own New POS till key role lacks ReadOrder ('add ReadOrder to that role yourself'), and a Dashboard refund 'stays Pending until an administrator settles it with two Admin API calls' in GraphiQL. _[quick-start text 'Optional: a device key for each till'; plugin-setup 'Settle a Dashboard refund']_

It also has the aside 'Not in the release notes: in 0.2.0 and 0.3.0 this role has no ReadOrder'. A visitor checking how active and mature the project is gets internal references instead of a plain summary. _[changelog/desktop/01; changelog/phone/01]_

Staff cannot scan it under pressure. _[troubleshooting.desktop.01-02 'Act on a header notice > Till updates line']_
- J3 (9): The optional device-key instructions send pnpm users to the GitHub README instead of linking the existing local section with the required configuration and verification steps. _[text/quick-start.txt:212; text/connect-a-till.txt, 'Make the key button available in a pnpm project']_
- J4 (8): On Troubleshooting, the "Orders line" and "Till updates line" labels are bold paragraphs, not headings, so they are missing from the On this page rail. ## Overall worst defect per judge

- **J1 First-time visitor** (C5): A first-time visitor who scrolls past the hero to decide whether to try it ends on server prerequisites ('Node ^20.19 || >=22.12', 'Postgres', 'RxDB Premium licence token (RXDB_PREMIUM)') and a paragraph of inline links. There is no closing Live demo button. The low-commitment next step that suits this visitor is only at the very top of a long, text-only page. _[home/desktop/02 'Before you start' to footer; home/phone/04-05]_ Fix: End the home page with a short closing band ('Try it in your browser', with Live demo and Quick start buttons), placed after or instead of the inline-link paragraph. Move the server prerequisites behind a 'For developers' heading or link them to the Overview's Requirements.
- **J2 Working shop owner** (C1): A shop owner's first question, 'what does my counter need for staff to sell tomorrow?', has its answer buried as one long bullet inside a developer-oriented 'Before you start' list (Node version ranges, RXDB_PREMIUM, Postgres), so the counter story never stands on its own on the home page. _[home.desktop.02 / home.phone.04 'Before you start']_ Fix: Split 'Before you start' into two short lists, 'At the counter' (a computer with desktop Chrome, a keyboard-style barcode scanner, any printer the browser can use, your own card terminal, one tab per till) and 'On your Vendure server' (Vendure 3.6+, Postgres, Node, the plugin).
- **J3 Developer evaluating it** (C3): A developer with both tax-inclusive and tax-exclusive channels must guess how to reconcile the recommended channel-dependent choices with the single store-wide tax strategy. _[Quick start, step 6, 'Why these pairings'; text/endpoint_llms_full_txt.txt:867–868]_ Fix: Document the supported configuration for mixed pricing modes and a totals check for each mode. If that configuration is unsupported, state the restriction explicitly.
- **J4 Designer** (C5): The home page ends in a heavy grey block. "Before you start" is a seven-bullet list set larger than every other body text on the page, mixing requirements (Vendure, Node, npm) with caveats (cash drawer, RxDB licence, coupons, refunds) already given in the table above. After a well-paced hero, feature grid and table, the page's rhythm collapses into its loudest and least-scannable section. _[home.desktop.02 / home.phone.04-05]_ Fix: Set the list to the same 15px secondary body size as the feature text. Keep only the four requirement bullets, and move the counter, licence and coupon/refund caveats into a single "See Limitations" line.
- **J5 Competitor-aware sceptic** (C2): A client asking 'who maintains this, and who do I call when the till stops selling?' finds no answer. No maintainer, organisation, support route or reference users are named. The only outside party mentioned is 'ph.wcpos.com', which is never explained. The plugin also has had no release for six weeks, while the docs carry a known role gap ('this role has no ReadOrder'). That combination makes it look like an unbacked side project. _[home/desktop/02 (table and footer 'MIT licensed. Built with TallyUI.'); changelog/desktop/01]_ Fix: Add one short 'Who builds this' block to the home footer or Overview. It should name the maintainer or organisation, say what wcpos.com is, and give a support or issue channel with expected response. Ship a 0.3.1 that adds ReadOrder to the till role, so the changelog shows maintenance after the launch week.
