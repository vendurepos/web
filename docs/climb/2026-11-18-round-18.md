## Worst defect per judge and criterion

### C1 First impression (mean 8.4)
- J1 (8): The first thing above the H1 is the badge 'Pre-release · plugin 0.3.0', and the line under the buttons ('Your own store needs the plugin on your Vendure server first: the quick start sets it up. Then try the till with your store.') talks about a plugin and a server before a newcomer knows there is one. Together with the four-line hero paragraph, that is a lot to read in five seconds next to two clear buttons. _[home/desktop/01 and home/phone/01 (hero)]_
- J2 (8): The hero is clear ("Point of sale for Vendure", a live till screenshot, Live demo and Quick start buttons), but the next line, "Your own store needs the plugin on your Vendure server first…", is written for a developer. The home page also never says what the counter needs (tablet or PC, browser, receipt printer, scanner). _[home.desktop.01 hero paragraph]_
- J3 (9): none found _[shots/home.desktop.01.jpg; text/home.txt]_
- J4 (9): On a 390 px screen the hero lead runs to seven lines of large grey text, padded by the parenthetical "(Vendure is an open-source headless commerce framework)", so the till screenshot only starts at the bottom of the first screen and the small grey note under the buttons competes with the buttons. _[home/phone/01]_
- J5 (8): The hero says what it is and offers Live demo / Quick start, but nowhere on the home page does it say who builds or maintains VendurePOS (footer: only 'MIT licensed. Built with TallyUI. For Medusa, see MedusaPOS.'). It also never says who should not use it, such as a multi-store retailer that needs integrated card terminals or a cash drawer, so a buyer can't place it against Square or Shopify POS. _[home desktop 01-02 hero and footer; home.txt]_

### C2 Credibility (mean 8.0)
- J1 (8): The home comparison table says the demo's only traffic is 'anonymous usage events to ph.wcpos.com, with no cookie'. Nothing on the home page says who wcpos.com is or why a VendurePOS demo reports to it, so a newcomer wonders whose product this really is. _[home/desktop/02 'Live demo or your own store' table, last row; home/phone/04]_
- J2 (8): The page is honest about refunds and lost unsent sales. The weak spot is "Web till only for now. Its browser tests run in desktop Chrome; other browsers are not tested yet." It leaves a shop owner unsure whether the counter iPad or tablet will work. Minor: the demo payment screenshot shows a product named "Tally Fixture Mug". _[limitations.desktop.01; at-the-till.desktop.02]_
- J3 (9): none found _[text/home.txt; text/limitations.txt; text/connect-a-till.txt]_
- J4 (9): Requirements and limits are blended together: "Before you start" on the home page mixes a limitation bullet ("Coupon codes are not supported yet ... refunds go through the Vendure Dashboard") into the requirements list, so the refund limit is said three times on one page (table row, this bullet, the link to Limitations). _[home/desktop/02, 'Before you start']_
- J5 (6): The home page sells an 'open-source till' that is 'MIT licensed', but building the till yourself 'needs your own RxDB Premium licence token in RXDB_PREMIUM' (a paid third-party licence). That is said only on Limitations and Connect a till, so in practice you depend on the hosted app.vendurepos.com, run by an unnamed operator whose analytics go to an unexplained ph.wcpos.com. _[home.desktop.02 footer vs limitations.desktop.01 bullet 3, connect-a-till.desktop.01 'The till's source is MIT-licensed...']_

### C3 Path to a till (mean 7.8)
- J1 (8): The quick start's opening paragraph gives two hosted addresses ('The hosted POS is live at https://app.vendurepos.com. https://vendurepos.vercel.app serves the same build.') and mentions the vercel address again under CORS. A newcomer is left unsure which one to open and allow, and the run-in sentence reads like a typo. _[quick-start/desktop/01 intro paragraph; quick-start/desktop/02 step 5]_
- J2 (7): To refund a sale in your own store you "refund in the Vendure Dashboard… Pending until an administrator settles it with the Admin API's settleRefund mutation". No page gives the steps or an example, so a shop owner cannot refund a customer tomorrow. _[at-the-till.desktop.02 "Refund a sale"; limitations.desktop.01]_
- J3 (8): The pnpm Dashboard example uses path.resolve(__dirname, 'node_modules') without naming the configuration file or showing the required path import. _[shots/connect-a-till.desktop.02.jpg, Make the key button available in a pnpm project]_
- J4 (8): Step 8 is a lettered list a–i inside a numbered step, and its item h ("check Vendure for the POS prices, settled tally-pos payment ...") repeats the "Check it worked" checklist directly below it. Step 9 "Troubleshoot" is then three long run-on bullets full of code chips (the CORS bullet is 5 lines on desktop and 11 on phone), so the success state and the fixes are hard to scan. _[quick-start/desktop/03-04; quick-start/phone/08]_
- J5 (8): The role the plugin's own 'New POS till key' button creates is missing ReadOrder on 0.3.0 ('On plugin 0.3.0 the role it creates (vendurepos-pos-till) has the step 4 permissions except ReadOrder, so add ReadOrder to that role yourself'). This is a known bug the docs work around in three places instead of a fixed release. _[quick-start.desktop.04 'Optional: a device key for each till'; connect-a-till.txt 'Give each cashier their own account' and 'Create and use a device key']_

The Changelog also cites 'ADR 0005' and '#116' with no links or meaning. _[connect-a-till/desktop/01 'Stored in this browser'; plugin-setup/desktop/01; changelog/desktop/01]_

The Changelog is written for developers ("order.create v5 custom lines… (ADR 0005)", "GET /tally/v1/info advertises order.create 1–5") and has no plain-language note for shop owners beyond "In short". _[at-the-till.desktop.03 Z report; changelog.desktop.01]_
- J3 (8): The current-version refund instructions stop at naming settleRefund and linking the general Admin API mutations reference, without an example showing how to settle the Pending POS refund. _[shots/at-the-till.desktop.02.jpg, Refund a sale; text/endpoint_llms_full_txt.txt]_
- J4 (8): Limitations is a flat list of 15 equal-weight bullets with no grouping. The one data-loss risk ("Sales not yet sent are kept only in this browser ... those sales are lost") sits 12th, between "One browser tab per till" and "The manager's approval ... is a typed name". _[limitations/desktop/01]_

But refunds at the till don't exist on any released plugin ('On plugin 0.3.0 an order shows no Refund items'), and the changelog never mentions TallyPosRefund, so the docs describe a permission no reader can find. _[at-the-till.txt 'Refund a sale' last paragraph vs changelog.desktop.01]_

## Overall worst defect per judge

- **J1 First-time visitor** (C2): The home page tells a first-time visitor that the demo sends usage events to ph.wcpos.com and never says who WCPOS is or how it relates to VendurePOS. On a product they have never heard of, an unexplained third-party domain is the line most likely to make them hesitate before trying the demo. _[home/desktop/02 and home/phone/04, 'Live demo or your own store' table, row 'Sales reach Vendure, once each, even offline']_ Fix: In that cell, say in a few words who runs ph.wcpos.com and that it is the same self-hosted PostHog this site uses (Connect a till already explains it), or link the words to that section.
- **J2 Working shop owner** (C3): On plugin 0.3.0, refunding a sale in your own store means the Vendure Dashboard plus "the Admin API's settleRefund mutation", and no page gives a shop owner steps they can follow. _[at-the-till.desktop.02 "Refund a sale"; limitations.desktop.01]_ Fix: Add a short "Refund a customer on plugin 0.3.0" how-to: the Dashboard clicks with a screenshot, plus a copy-paste settleRefund example for the developer. Link it from the refund row of the home page's demo-vs-store table.
- **J3 Developer evaluating it** (C3): The pnpm device-key setup example requires the developer to infer its configuration file and supply the missing path import. _[shots/connect-a-till.desktop.02.jpg, Make the key button available in a pnpm project]_ Fix: Name the Dashboard Vite configuration file and include the required import. State which directory nodeModulesRoot must resolve to and tell the reader to rebuild the Dashboard and verify that New POS till key appears.
- **J4 Designer** (C5): The docs entry page ends with redundant components: the "Next steps" cards include "Quick start", and directly under them a full-width pager card also says "Quick start >" with near-identical text, while the sidebar highlights both "Docs" and "Overview". On phone this stacks four cards, two of them to the same page, and it reads as default template output rather than a designed page. _[docs/desktop/01; docs/phone/02]_ Fix: Replace the "Quick start" card in Next steps with "Plugin setup" (or hide the pager on the Overview page), and highlight only "Overview" in the sidebar when on /docs.
- **J5 Competitor-aware sceptic** (C2): 'MIT licensed' and 'open-source till' on the home page hide two facts a client would ask about first: the till can't be built without a paid RxDB Premium licence, and the hosted app.vendurepos.com you'd otherwise depend on has no named operator, maintainer or support/continuity statement anywhere on the site. That's the lock-in and abandonment risk I'd warn a client about. _[home.desktop.02 footer / 'Before you start'; limitations.desktop.01 bullet 3; connect-a-till.desktop.01]_ Fix: Add one line to the home page's 'Before you start': 'Use the hosted till at app.vendurepos.com, or self-build it, which needs a paid RxDB Premium licence.' Add one footer line naming who runs VendurePOS and the hosted app, with a link to the maintainer.
